## 一、已核实正确的部分

### 1. 拒绝自己给叶片打分 —— 最关键的一条

E14 要 150 张人工分级。接手方明确拒绝代劳,理由是模型去评模型自己的代理指标,
会让 E14 变成自证。

这个判断是对的,而且比它自己陈述的更重要:E13 的 AUC 0.868 只证明"病斑面积比
能区分健康与患病";RQ3 问的是估计**可不可信**,只有 E14 的 ρ 和 κ 能回答。若由
模型代评,RQ3 在整份报告里就没有任何独立证据支撑。

### 2. 分级错位是真 bug,逐档核实吻合

`outputs/annotation/annotator_1/INSTRUCTIONS.txt` 写明 `1 = mild, < 5%`,
而旧阈值 `[0.05, 0.20, 0.50]` 使 `<5%` 落入 `healthy = 0`,整体错开一级。
`probe_severity_validate` 是 `levels.index(estimated_level)` 对 `int(manual_grade)`
逐 index 比对,**一个完全遵守说明书的标注者会被判为不一致**。

修正后对齐(已逐档核对):

| 病斑占比 | 估计器 | 说明书 |
|---|---|---|
| < 0.5% | healthy = 0 | "0 可能但应少见" |
| 0.5 – 5% | mild = 1 | mild = 1 |
| 5 – 20% | moderate = 2 | moderate = 2 |
| > 20% | severe = 3 | severe = 3 |

核实项:

- 标注样本 150 张的 `estimated_level` 分布 = `mild 32 / moderate 53 / severe 65`,
  与它报告的 `0/32/53/65` **一张不差**。
- `severity_probe.json` 的 AUC = `0.8676` (official) / `0.7670` (Otsu),
  与修改前一致 —— 因为 E12/E13 走的是**连续比值**,阈值不参与。这个推理成立。
- 四个标注包内容为 `no, image, manual_grade`,不含 level,所以**改阈值不影响
  已生成的 zip**,可以直接发出。此点核实无误。

若未发现,E14 会产出一个**捏造的负面结果**:模拟一个完美标注者,
exact agreement 会是 0.153 而非 0.847,κ 0.629 而非 0.904。而 ρ 因为是基于连续
比值的秩相关**不受影响** —— 也就是说这个错误会被部分掩盖,更难发现。

### 3. 尺度假设成立,且是全新方向

已核实:`src/training/augment.py:42` 用 `RandomResizedCrop(image_size, scale=(0.5, 1.0))`,
`src/data/plantvillage.py:24` 用 `scale=(0.8, 1.0)`。**两个配方都没有 scale > 1
的分支。**

`RandomResizedCrop` 的 `scale` 是所裁子区域占原图面积的比例,裁完再放大到
`image_size`。因此 scale ≤ 1 意味着**只会把叶片放大,从不缩小**。

PlantVillage 叶片平均占画面 47.5%(`outputs/gradcam_audit.json`,E5 的基线),
增广只把这个比例往上推。田间照片里一片叶子占整株画面的比例远低于此,
**落在训练支撑集之外**。

这一点此前没有任何一个臂触及:E8 改的是叶子**背后**是什么,E9 是**去掉**背景,
E15 是**多少参数**在动。没有一个臂改过**叶子有多大**。这比现有文本更好地解释了
E8 仅 +0.42 的结果。

### 4. 长宽比问题属实

评估路径为 `transforms.Resize((image_size, image_size))`(`src/data/plantvillage.py:34`),
不保持长宽比。PlantVillage 是 256×256 方图,无影响;PlantDoc 是任意长宽比的
网络照片,**全部被压扁**。这是一个只作用于田间集、不作用于实验室集的形变。

接手方判断"修改共享评估变换会破坏与全部已有数字的可比性,必须另开一臂而非直接
改",这个克制是正确的。

### 5. 预注册纪律保持住了

E20 的证伪条件在开跑前写定:若作物准确率在 2,525 张基准上未超过 E8 逾 ±1.7pp,
则 H10 被拒。没有出现事后放宽条件的迹象。

## 二、必须修的三处

### 1. 阈值改动尚未提交(优先)

`git status` 显示 `configs/default.yaml` 与 `docs/EXPERIMENTS.md` 仍在工作区未提交。
这是**预注册相关**的变更,必须进入版本历史,否则无法证明它发生在人工标注**之前**。
这恰恰是这次修正最重要的合法性依据。

### 2. "300 张患病叶"的表述有误

`diseased_grade_distribution` 合计为 **150**,不是 300;`n: 300` 是 150 健康 +
150 患病的总数。表述为"of 300 leaves the dataset labels diseased"不准确,
抄进报告会被质疑。

### 3. 决定 H9 的数字不在训练日志里

`scripts/train.py` 只输出 PlantDoc 总准确率,且只在 236 张 test 上;
**作物准确率来自 `scripts/evaluate.py`**,仅在 `eval_arm_*` 阶段产生。

且必须**同底比较**:`eval_arm_hier` 与 `eval_arm_bg_random` 都基于全部 2,525 张,
可以直接对比;`train_hier` 打印的 236 张数字不能与之并列。

延伸影响(接手方自己指出,正确):`docs/EXPERIMENTS.md` 现有的分解表
(46.19% × 52.29% = 24.15%)本身也是 n=236 的。等 `eval_arm_bg_random` 落地后,
**整张表需要在 2,525 张基准上重述**,否则 E17 会被拿去和一个不同基准的基线比较。

## 三、073 的缺口

`073` 在整个仓库只出现 **2 次**,均为 `configs/experiments.yaml` 中的 stage 标签:

- `efficiency` → `073-3 deployment profile`
- `finetune_full` → `E11 / 073-1 full-data adaptation`

而在 `docs/EXPERIMENTS.md`、`README.md`、`CLAUDE.md` 中出现 **0 次**,
且 **073-2 完全缺失**。

现状是:PlantDoc 全量适应与部署效率剖析这两块**实质工作已完成**,但没有任何
文档说明 073 要求什么、哪一条对应哪一条。对评分者而言,没有映射等于没做。

**此项为原始交接文档的遗漏**:`CLAUDE.md` 与 `docs/HANDOFF.md` 完全未提 073,
接手方没有任何线索可循,不应归咎于接手方的大局观。

补齐需要 073 的 brief 原文(尤其 073-2 的内容),然后:

1. 在 `docs/EXPERIMENTS.md` 增加 073 需求映射表,与现有的 rubric 映射表并列
2. 补全 `configs/experiments.yaml` 中散落的 073 标签,使编号连续
3. 在 `CLAUDE.md` 与 `docs/HANDOFF.md` 写明两个项目的关系

口径按既定原则:**不声称"同时完成了两个项目"**,但两边要求均需实质满足且可追溯。
